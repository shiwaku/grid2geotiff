# 設計メモ

なぜこの実装になっているかを書く。使い方は [README](../README.md) にある。

「森林資源データ解析・管理標準仕様書 Ver3.1」はこう書いている。

> 一般のレーザ計測成果としては、XYZ 座標値（テキスト形式）で作成されるが、各種解析に利用するにはラスタ（TIFF 形式）への変換が必要となる。

この変換には、素朴にやると間違える点が3つある。

## 1. 座標はセル中心なので半セルずれる

グリッドデータの座標は**セルの中心**を指す。これは推測ではなく規程に書いてある。国土地理院「航空レーザ測量による数値標高モデル（ＤＥＭ）作成マニュアル（案）」第8節（メッシュデータ作成）の運用基準はこう定める。

> メッシュデータの位置は、国土基本図単位に、南北及び東西方向に、それぞれ任意間隔で分割して得られる**各メッシュの中心位置**とする。

実データもそのとおりで、山梨県なら `5600.25 -36900.25 271.95` のように `.25` / `.75` で並ぶ。これをそのままラスタの原点にすると、全体が**半セル（0.5m 格子なら 0.25m）ずれる**。

原点を `xmin - res/2` に置き、`AREA_OR_POINT=Area` を明示する。値自体は点標本だが、`Point` 規約は解釈がソフトによって割れるため、どの GIS でも同じ位置に載る `Area` で統一している（GDAL の XYZ ドライバと同じ流儀）。元が点標本であることは `GRID_CONVENTION` タグに残す。

## 2. グリッドデータと不規則点群は別物

格子状に並んだ点は、インデックス計算で**直接配置**できる。内挿は不要であり、してはいけない（元の値が壊れる）。一方、不規則点群のラスタ化は内挿補間（TIN / IDW / Kriging など）を伴う別の作業で、手法の選択が成果物に焼き込まれる。

入力の格子性を検証し、格子に載っていなければ**黙って内挿せずエラーにする**。検証は2段構えになっている。

### まずセルの埋まり具合を見る

```console
$ grid2geotiff convert scatter.txt -o out --crs EPSG:6676
  NG   scatter.txt  格子が疎すぎる（点 30,000 に対して 99,746x74,783 =
       7,459,305,118 セル、充填率 0.0004% < 許容 1.0000%）。推定した格子間隔
       0.001 x 0.001 m が実際の間隔と合っていない。…
```

格子間隔は「座標のユニーク値の差分の最頻値」で推定する。しかし散らばった点では、テキストの桁数による量子化ステップを拾ってしまう（`%.3f` で書かれていれば 0.001m）。するとすべての点がその細かい格子にぴったり載るため、**ずれを見るだけの検定は素通りする**。

判定指標は実データで測って選んだ。

| | 最頻値の占有率 | 充填率 | 幅 / ユニーク X |
|---|---:|---:|---:|
| 実データ（山梨県 08LE2134） | 100.00% | 99.6% | 1.00 |
| 散布データ `%.3f` | 51.80% | 0.0004% | 4.87 |
| 散布データ `%.6f` | 0.17% | 0.000008% | 130.94 |

**充填率だけが桁違いに分離する。** 既定の下限は 1%。静岡県 ALB の実データ 1,164 図郭で最も疎なものが 4.34% だったので、4 倍以上の余裕がある。

この検定は残差検定より前に置いている。格子間隔の推定が外れていると、残差の数値（「推定間隔 0.000127 m」など）が無意味になって原因を追えないため。

### 格子間隔が分かれば、格子からのずれを見る

```console
$ grid2geotiff convert scatter.txt -o out --crs EPSG:6676 --res 0.5
  NG   scatter.txt  X 軸が格子に載っていない（最大ずれ 0.25 m > 許容 0.005 m、
       推定間隔 0.5 m）。不規則点群の可能性が高く、ラスタ化するには内挿補間が必要
```

## 3. 座標系の取り違えは後から気づけない

国土基本図の図郭番号は**先頭2桁が平面直角座標系の系番号**になっている。`08LE2134` なら第8系。JGD2011 の平面直角座標系は EPSG:6669（第1系）から連番なので、系番号 N に対して `EPSG = 6668 + N` で求まる。第8系なら 6676 である。

そこで `--crs` を省略すると、ファイル名を図郭番号として読んで CRS を判定する。

### 解釈できる形式

末尾に `_dsm` のような注記が付いていてもよい。

| 例 | 地図情報レベル | 図郭の大きさ | 0.5m 格子での点数 |
|---|---|---|---:|
| `08LE21` | 1/5000 | 4km × 3km | 4,800万 |
| `08LE213` | 1/2500 | 2km × 1.5km | 1,200万 |
| `08LE2134` | 1/1000 | 800m × 600m | 192万 |
| 〃 | 1/500 | 400m × 300m | 48万 |
| 〃 | 1/2500 の4分割 | 1km × 750m | 300万 |

最後の3行が同じ例なのは誤記ではない。**数字2桁の読み方が3通りある**。どれも 1/5000 コードの後ろに数字2桁が付く形で、1/1000 は縦横5等分なので各桁 0〜4、1/2500 の4分割は番号が 1〜4 になる。そこで全部を候補として範囲を計算し、**実際の座標が収まるものを細かい方から採る**。大きさが3通りとも違うので、座標を見れば一意に決まる。系番号は先頭2桁からしか決まらないので、どれに転んでも CRS は同じであり、判定を外しても位置がずれることはない。

**1/2500 の4分割は準則の地図情報レベルではない。** 林野庁「マップタイル作成マニュアル 第1.0版」が「ラスタデータにあっては国土基本図図郭（2,500 やその４分の１）…を単位として作成されることが多い」と書く実務上の単位で、広島県の航空レーザ計測データ（2000×1483 @0.5m）がこれにあたる。相当する地図情報レベルが無いので、呼称をそのまま「1/2500 の4分割」としている。

**1/5000 より粗い図郭は受け付けない。** XYZ テキストの点数は図郭サイズ ÷ 格子間隔で決まるので、大きい図郭はそもそもテキストで配布されない。

- 1/50000 図郭（`08LE` の4文字）…… `12AB` のような文字列と見分けがつかず誤判定しやすい
- 1/50000 を4分割した図郭（`04HE2` の5文字、南北 15km × 東西 20km）…… ラスタや GeoPackage の配布単位であって XYZ の単位でない

### 図郭の割り方

系原点を中心に南北 ±300km・東西 ±160km の区域を縦 20・横 8 に分割すると、南北 30km × 東西 40km の長方形になる。左上を A として南北・東西の順に記号を付す。以下、1/5000（縦横 10 等分）・1/2500（4 等分）・1/2500 の4分割（さらに 4 等分）・1/1000（縦横 5 等分）・1/500（縦横 10 等分）へ細分する。

この規則は「森林情報に関するオープンデータ標準仕様書 Ver2.1」参考3（20m メッシュ ID の付与規則）で確認し、山梨県の実データ4枚の座標範囲と完全に一致することを検算した。

**基準は 1/2500 である。** 国土地理院「航空レーザ測量による数値標高モデル（DEM）作成マニュアル（案）」第2条は、国土基本図図郭を「各系の原点を基準に、南北 1.5km、東西 2.0km の区画に区分」したものと定義し、「データ区分は、国土基本図単位を基本とする」と定める。

4等分の番号の並び（1=北西, 2=北東, 3=南西, 4=南東）は仕様書の図版でしか示されていないが、広島県の航空レーザ計測データ 300 図郭について、計算した範囲に実際の座標が収まることを確かめてある。

### 検算とその限界

推測が外れると成果物の位置が丸ごとずれるうえ、CRS は埋め込まれてしまい後から気づきにくい。そこで図郭番号から範囲も計算し、実際の座標がその図郭に収まることを確かめてから採用する。

```console
$ grid2geotiff convert 08LE2144.txt -o out
  NG   08LE2144.txt  図郭番号 08LE2144 から EPSG:6676 と判定したが、座標範囲
       X 5600.00..6000.00 Y -37200.00..-36900.00 が図郭の範囲に収まらない
       （1/500 は X 5600.00..6000.00 Y -37500.00..-37200.00、
         1/1000 は X 7200.00..8000.00 Y -39000.00..-38400.00、
         1/2500 の4分割 は X 7000.00..8000.00 Y -39000.00..-38250.00）。…
```

**この検算で分かるのは「ファイル名が本当に図郭番号か」と「どの階層の図郭か」であって、系番号の正しさは検証できない。** 図郭の範囲は各系の原点からの相対位置で決まるため、系を取り違えても範囲はまったく同じになる（`08LE2134` と `09LE2134` は各系で同じ位置を指す）。座標値だけから系を言い当てる方法はない。

それでも検算には意味がある。`12AB3456` のような業務番号がたまたま図郭番号の形に一致することはありうるが、その場合に座標が 400m × 300m の図郭にぴったり収まることはまずない。つまりこの検算は、名前の形が偶然一致しただけのファイルにでたらめな CRS を埋め込む事故を防ぐ。

系番号そのものは検証しようがないので、**判定した CRS は必ずログに出す**。確実を期すなら `--crs` で明示する（明示した値が常に優先される）。

## 図郭のマージ

「マップタイル作成マニュアル 第1.0版」はこう書いている。

> QGIS では、経験上、データファイル数が 100 を超えてくると動作が重くなることから、ある程度取り回しの良いサイズにラスタデータをマージし、マージされたラスタでエラーがないか確認するほうが効率がよい

### VRT を経由する

VRT は実データを持たず「どのファイルのどこを、出力のどこに置くか」だけを記した XML なので、何千枚を並べてもメモリに載らない。GDAL の Python バインディングに依存しない方針を保つため、XML は自前で組み立てている。

読み書きはブロック単位で流すので、**1600 × 1800 の結合で実測ピーク 0.5MB**（一括で持てば 11MB）。

VRT に書くソースのパスは、相対パスと絶対パスの短いほうを選ぶ。出力をソースと同じ場所に置けばファイル名だけになり、VRT ごと持ち運べる。共通の親が遠くて `..` が延々と並ぶ場合は絶対パスにする。

NoData は `ComplexSource` の `NODATA` で吸収するので、図郭ごとに値が不揃いでも出力側の1つの値に統一できる。

### 揃っていない入力は結合しない

座標系・格子間隔・データ型に加えて、**格子の位相**を確かめる。

```console
$ grid2geotiff merge base.tif half.tif -o out.tif
  NG   half.tif の格子が base.tif と噛み合わない（X 方向に 0.25 m ずれている）。
       そのまま結合すると値がセル単位でずれる
```

ここを見ないと、半セルずれた図郭を VRT が黙って最近隣で丸め込む。**半セルずれはこのツールが最初に取り組んだ問題そのもの**なので、結合で作り直すわけにいかない。

### 離れた区画は弾く

別々の地域の図郭をまとめて指定すると、間を埋めるだけの巨大な空ラスタができる。静岡県 ALB の全 1,164 図郭（沿岸に散在）で試すと 213,925 × 117,770 = **251 億セル・被覆率 1.31%** になり、GeoTIFF として書けば約 100GB になる。

穴あきの結合そのものは通す。実測で被覆率 35.87%（静岡県の 1/5000 図郭ひとつ、54 枚）と 66.67%（山梨県、4 枚）のケースを確認済み。

なお `--vrt-only` なら実体を作らないので、被覆率が低くても 486KB の XML で済む。この場合は `--min-coverage 0` で明示的に通す。

## 結合の正しさをどう確かめたか

結合後の有効セル数が図郭ごとの有効セル数の合計と一致すれば、隙間があれば減り重複があっても減るので、**両方ないと言える**。

| データ | 出力 | 有効セル |
|---|---|---|
| 山梨県 甲府 6 図郭 | 1,600 × 1,800 | 2,869,839 = 図郭の合計 |
| 静岡県 ALB `08PD13` 54 図郭 | 7,655 × 6,000 | 11,043,678 = 図郭の合計 |
