# grid2geotiff

航空レーザ計測のグリッドデータ（XYZ座標値テキスト）を GeoTIFF に変換する CLI。

セル中心で記録された座標を**半セルずらして**配置するため、出力が国土基本図の図郭境界にぴったり載る。格子に載っていない点群は**内挿せずエラーにする**。ファイル名が図郭番号なら、座標系も自動で判定する。

```console
$ grid2geotiff convert data/raw -o data/out -j 4
変換 4 ファイル -> data/out  (CRS は図郭番号から判定 / JGD2011)
  OK   08LE2134.txt  800x600 @ 0.5m  点 478,294  欠損 1,706 (0.36%)  CRS EPSG:6676（1/500 図郭番号から推定）  -> 08LE2134.tif
  OK   08LE2135.txt  800x600 @ 0.5m  点 480,000  欠損 0 (0.00%)  CRS EPSG:6676（1/500 図郭番号から推定）  -> 08LE2135.tif
  OK   08LE2144.txt  800x600 @ 0.5m  点 480,000  欠損 0 (0.00%)  CRS EPSG:6676（1/500 図郭番号から推定）  -> 08LE2144.tif
  OK   08LE2145.txt  800x600 @ 0.5m  点 471,545  欠損 8,455 (1.76%)  CRS EPSG:6676（1/500 図郭番号から推定）  -> 08LE2145.tif

変換: 成功 4 / 失敗 0 / 計 4
```

## なぜこれが要るのか

「森林資源データ解析・管理標準仕様書 Ver3.1」はこう書いている。

> 一般のレーザ計測成果としては、XYZ 座標値（テキスト形式）で作成されるが、各種解析に利用するにはラスタ（TIFF 形式）への変換が必要となる。

この変換には、素朴にやると間違える点が3つある。

### 1. 座標はセル中心なので半セルずれる

グリッドデータの座標は**セルの中心**を指す。山梨県のデータなら `5600.25 -36900.25 271.95` のように `.25` / `.75` で並ぶ。これをそのままラスタの原点にすると、全体が**半セル（0.5m格子なら0.25m）ずれる**。

本ツールは原点を `xmin - res/2` に置き、`AREA_OR_POINT=Area` を明示する。値自体は点標本だが、`Point` 規約は解釈がソフトによって割れるため、どの GIS でも同じ位置に載る `Area` で統一している（GDAL の XYZ ドライバと同じ流儀）。元が点標本であることは `GRID_CONVENTION` タグに残す。

### 2. グリッドデータと不規則点群は別物

格子状に並んだ点は、インデックス計算で**直接配置**できる。内挿は不要であり、してはいけない（元の値が壊れる）。一方、不規則点群のラスタ化は内挿補間（TIN / IDW / Kriging など）を伴う別の作業で、手法の選択が成果物に焼き込まれる。

本ツールは入力の格子性を検証し、格子に載っていなければ**黙って内挿せずエラーにする**。

検証は2段構えになっている。**まずセルの埋まり具合を見る。**

```console
$ grid2geotiff convert scatter.txt -o out --crs EPSG:6676
  NG   scatter.txt  格子が疎すぎる（点 30,000 に対して 99,746x74,783 =
       7,459,305,118 セル、充填率 0.0004% < 許容 1.0000%）。推定した格子間隔
       0.001 x 0.001 m が実際の間隔と合っていない。不規則点群ならラスタ化するには
       内挿補間が必要。格子間隔が分かっているなら --res で指定する
       （意図的に疎な格子なら --min-fill-ratio で緩める）
```

格子間隔は「座標のユニーク値の差分の最頻値」で推定するが、散らばった点ではテキストの桁数による量子化ステップを拾ってしまう（`%.3f` で書かれていれば 0.001m）。するとすべての点がその細かい格子にぴったり載るため、**ずれを見るだけの検定は素通りする**。格子データなら点数とセル数はほぼ一致する（実データの充填率は 98% 以上）ので、桁違いに疎ければ格子ではない。

**格子間隔が分かっていれば、次に格子からのずれを見る。**

```console
$ grid2geotiff convert scatter.txt -o out --crs EPSG:6676 --res 0.5
  NG   scatter.txt  X 軸が格子に載っていない（最大ずれ 0.25 m > 許容 0.005 m、
       推定間隔 0.5 m）。不規則点群の可能性が高く、ラスタ化するには内挿補間が必要
```

### 3. 座標系の取り違えは後から気づけない

国土基本図の図郭番号は**先頭2桁が平面直角座標系の系番号**になっている。`08LE2134` なら第8系。JGD2011 の平面直角座標系は EPSG:6669（第1系）から連番なので、系番号 N に対して `EPSG = 6668 + N` で求まる。第8系なら 6676 である。

そこで `--crs` を省略すると、ファイル名を図郭番号として読んで CRS を判定する。解釈できる形式は次のとおり（末尾に `_dsm` のような注記が付いていてもよい）。

| 例 | 地図情報レベル | 図郭の大きさ | 0.5m 格子での点数 |
|---|---|---|---:|
| `08LE21` | 1/5000 | 4km × 3km | 4,800万 |
| `08LE213` | 1/2500 | 2km × 1.5km | 1,200万 |
| `08LE2134` | 1/1000 | 800m × 600m | 192万 |
| 〃 | 1/500 | 400m × 300m | 48万 |

最後の2行が同じ例なのは誤記ではない。1/1000 と 1/500 はファイル名の形が同じで、名前だけでは区別できない（後述）。

図郭番号でない名前なら、これまでどおり `--crs` を要求する。

**1/5000 より粗い図郭は受け付けない。** XYZ テキストの点数は図郭サイズ ÷ 格子間隔で決まるので、大きい図郭はそもそもテキストで配布されない。1/50000 図郭（`08LE` の4文字）は `12AB` のような文字列と見分けがつかず誤判定しやすいため、1/50000 を4分割した図郭（`04HE2` の5文字、南北 15km × 東西 20km）はラスタや GeoPackage の配布単位であって XYZ の単位でないため、どちらも弾く。

**1/1000 と 1/500 はファイル名の形が同じ**で、どちらも 1/5000 コードの後ろに数字2桁が付く（1/1000 は縦横5等分なので各桁 0〜4）。そこで両方を候補として範囲を計算し、**実際の座標が収まる方を採る**。系番号は先頭2桁からしか決まらないので、どちらに転んでも CRS は同じであり、判定を外しても位置がずれることはない。

```console
$ grid2geotiff convert dsm_area1.txt -o out
  NG   dsm_area1.txt  ファイル名から CRS を判定できない（図郭番号の形式でない:
       'dsm_area1'）。--crs で明示すること
```

推測が外れると成果物の位置が丸ごとずれるうえ、CRS は埋め込まれてしまい後から気づきにくい。そこで図郭番号からは範囲も計算し、実際の座標がその図郭に収まることを確かめてから採用する。

```console
$ grid2geotiff convert 08LE2144.txt -o out
  NG   08LE2144.txt  図郭番号 08LE2144 から EPSG:6676 と判定したが、座標範囲
       X 5600.00..6000.00 Y -37200.00..-36900.00 が図郭の範囲に収まらない
       （1/500 は X 5600.00..6000.00 Y -37500.00..-37200.00、
         1/1000 は X 7200.00..8000.00 Y -39000.00..-38400.00）。
       ファイル名が図郭番号でない可能性がある。--crs で明示すること
```

**この検算で分かるのは「ファイル名が本当に図郭番号か」と「どの階層の図郭か」であって、系番号の正しさは検証できない。** 図郭の範囲は各系の原点からの相対位置で決まるため、系を取り違えても範囲はまったく同じになる（`08LE2134` と `09LE2134` は各系で同じ位置を指す）。座標値だけから系を言い当てる方法はない。

それでも検算には意味がある。`12AB3456` のような業務番号がたまたま図郭番号の形に一致することはありうるが、その場合に座標が 400m × 300m の図郭にぴったり収まることはまずない。つまりこの検算は、名前の形が偶然一致しただけのファイルにでたらめな CRS を埋め込む事故を防ぐ。

系番号そのものは検証しようがないので、**判定した CRS は必ずログに出す**。確実を期すなら `--crs` で明示する（明示した値が常に優先される）。

## インストール

```console
pip install -e .
```

Python 3.10 以上。依存は rasterio / numpy / pandas / click のみで、GDAL の Python バインディングは不要。

## 使い方

### convert — GeoTIFF に変換する

```console
grid2geotiff convert <入力...> -o <出力先> [--crs <EPSG>]
```

入力にはファイルのほかディレクトリも指定できる（再帰探索）。`--crs` を省略するとファイル名の図郭番号から判定する。

| オプション | 既定 | 説明 |
|---|---|---|
| `--crs` | 図郭番号から判定 | 入力座標の参照系（例 `EPSG:6676` = JGD2011 平面直角座標系第8系） |
| `--datum` | `jgd2011` | 図郭番号から判定するときの測地系。`jgd2011` / `jgd2000` |
| `-o, --out-dir` | 必須 | GeoTIFF の出力先 |
| `--res` | 自動推定 | 格子間隔 [m]。`0.5` か `0.5,0.5` |
| `--nodata` | `-9999` | 出力の NoData 値 |
| `--dtype` | `float32` | `float32` / `float64` / `int16` / `int32` |
| `--compress` | `deflate` | `deflate` / `lzw` / `zstd` / `none`（予測子2つき） |
| `--blocksize` | `256` | タイル化のブロックサイズ |
| `--delimiter` | 自動判定 | `space` / `comma` / `tab` / `semicolon` |
| `--columns` | `0,1,2` | X,Y,Z の列番号（0 始まり） |
| `--input-nodata` | なし | 入力側の欠測値。複数指定可 |
| `--tolerance-ratio` | `0.01` | 格子からのずれの許容量（格子間隔に対する比） |
| `--min-fill-ratio` | `0.01` | セル数に対する点数の下限。下回れば格子とみなさない |
| `-j, --jobs` | `1` | 並列処理数 |
| `--overwrite` | off | 既存の出力を上書き |

### inspect — 変換せずに点検する

大量の図郭を変換する前に、格子間隔の食い違いや不規則点群の混入を洗い出す。

```console
$ grid2geotiff inspect data/raw -j 4
点検 4 ファイル
  OK   08LE2134.txt  800x600 @ 0.5m  点 478,294  欠損 1,706 (0.36%)  X 5600.00..6000.00 Y -37200.00..-36900.00  CRS EPSG:6676（1/500 図郭番号から推定）
  OK   08LE2135.txt  800x600 @ 0.5m  点 480,000  欠損 0 (0.00%)  X 6000.00..6400.00 Y -37200.00..-36900.00  CRS EPSG:6676（1/500 図郭番号から推定）
```

`convert` と同じ判定を行うので、大量に変換する前にどの CRS が埋め込まれるかを確認できる。点検では CRS を判定できなくても失敗にはせず、理由を添えて報告する。

オプションは上の表のうち出力に関わらないもの（`--crs` / `--datum` / `--res` / `--delimiter` / `--columns` / `--input-nodata` / `--tolerance-ratio` / `--min-fill-ratio` / `-j`）がそのまま使える。

## 入力形式

`X Y Z` を1行1点で並べたテキスト。

- 拡張子: `.txt` / `.csv` / `.xyz` / `.dat`、およびそれを1つだけ含む `.zip`
- 区切り: 空白 / カンマ / タブ / セミコロン（先頭行から自動判定）
- 改行: LF / CRLF どちらも可
- `#` で始まる行と空行は読み飛ばす

## 出力仕様

- GeoTIFF（タイル化、既定 256×256 ブロック、Deflate + 予測子2）
- 1バンド、バンド説明 `elevation`（データ型は既定 `float32`、`--dtype` で変更）
- NoData 既定 `-9999`（欠損セルに充填。マップタイル作成マニュアルの「ラスタ値は -9999 に統一」に準拠）
- `AREA_OR_POINT=Area`、`GRID_CONVENTION` / `GRID_RESOLUTION` / `SOURCE_FILE` タグ

## サンプルデータ

山梨県の点群データ（CC BY 4.0 / ODbL デュアルライセンス）で動作確認できる。

```console
pip install mapbox-vector-tile
python scripts/fetch_yamanashi_sample.py --out data/raw
grid2geotiff convert data/raw -o data/out -j 4
```

配布リソースの URL は `{z}/{x}/{y}.pbf` のベクトルタイルだが、これは実データではなく**ダウンロード用の索引**である。タイルのフィーチャ属性に図郭番号（`MESH_NO`）と ZIP の URL が入っており、スクリプトはそこから実ファイルを辿る。

取得できるのは 1/500 図郭（400m × 300m）単位の 0.5m 格子で、1枚あたり 800 × 600 = 480,000 点。座標系は JGD2011 平面直角座標系第8系（EPSG:6676）で、図郭番号 `08LE2134` の先頭2桁から判定できるため `--crs` は要らない。

## 開発

```console
pip install -e ".[dev]"
pytest -q
ruff check . && ruff format --check .
```

テストは実データを使わず、同じ性質（セル中心座標・欠損セル・CRLF）を持つ合成データで検証する。ただし図郭番号から計算する範囲の期待値だけは、実データ4枚の座標範囲から採っている。
